# Niagara clipboard T3D

What Unreal writes when you press Ctrl+C in a Niagara **script graph** — the Scratch Pad, and
the module / dynamic-input / function script editors, which all share one view model
(`FNiagaraScriptGraphViewModel`).

Everything below was read off a real UE 5.8 capture unless marked otherwise. The capture was
taken twice across a full editor restart and came back **byte-identical**, which is what makes
hand-authored payloads viable at all — see [Type indices](#type-indices).

**Round trip confirmed.** A payload built entirely by `niagara/emit-t3d.mjs` — never near an
editor — was pasted into a UE 5.8 scratch pad and arrived with all eight nodes, every wire, the
Map Get parameter pins and their inline defaults intact. Hand-authored Niagara T3D works.

## The shape: a wrapper around Base64

Unlike the Material Editor, which puts node T3D straight on the clipboard, Niagara wraps it:

```
Begin Object Class=/Script/NiagaraEditor.NiagaraClipboardContent Name="NiagaraClipboardContent_2" ExportPath="/Script/NiagaraEditor.NiagaraClipboardContent'/Engine/Transient.NiagaraClipboardContent_2'"
   Begin Object Class=/Script/NiagaraEditor.NiagaraScriptVariable Name="NiagaraScriptVariable_13" ExportPath="…"
   End Object
   …one empty declaration per script variable…
   Begin Object Name="NiagaraScriptVariable_13" ExportPath="…"
      Variable=(VarData=(0,0,128,63,…),Name="Particles.DynamicMaterialParameter")
      Metadata=(Description=NSLOCTEXT("", "AF29…", "…"),VariableGuid=35F0…)
      DefaultValueVariant=(Bytes=(0,0,128,63,…),CurrentMode=Bytes)
      bSubscribedToParameterDefinitions=True
      ChangeId=5D95…
   End Object
   …one filled block per script variable…
   ExportedNodes="QmVnaW4gT2JqZWN0IENsYXNzPS9TY3JpcHQvTmlhZ2FyYUVkaXRvci5OaWFnYXJhTm9kZUlucHV0…"
End Object
```

- `ExportedNodes` is `FBase64::Encode` over the UTF-8 of an ordinary
  `FEdGraphUtilities::ExportNodesToText` dump. **Its line endings are CRLF.**
- Sub-objects use UE's two-pass form: every one is declared empty first, then reopened with
  `Begin Object Name=…` to carry its properties.
- `ExportPath` here is `ExportPath="Class'Path'"` — the whole thing double-quoted with the path
  in single quotes. The Material Editor writes the other arrangement (`ExportPath=Class'"Path"'`).
  Match the editor you are targeting.
- **`ScriptVariables` are optional for a paste.** They carry parameter metadata (description,
  default value, `VariableGuid`); the parameters themselves are rebuilt from the pins.
  Omitting them costs tooltips and defaults, not wiring. *(Inferred from the paste path —
  `FNiagaraScriptGraphViewModel::PasteNodesHere` collects them into a `VarsToAdd` local it never
  reads — and not yet confirmed by a round trip.)*

The import side only accepts `UNiagaraClipboardContent` (`FNiagaraClipboardContentTextObjectFactory::CanCreateClass`).
There is **no version or GUID gate**: get the class name and the shape right and foreign text
is accepted.

## Inner nodes

Plain `UEdGraphNode` T3D — the same encoding Blueprint uses, which is why blueprintue's
renderer draws it with no help from us:

```
Begin Object Class=/Script/NiagaraEditor.NiagaraNodeParameterMapGet Name="NiagaraNodeParameterMapGet_6" ExportPath="/Script/NiagaraEditor.NiagaraNodeParameterMapGet'/Engine/Transient.ScratchModule:NiagaraScriptSource_0.NiagaraGraph_0.NiagaraNodeParameterMapGet_6'"
   PinOutputToPinDefaultPersistentId=((218532E6…, D8CB9393…),(D437D7FC…, BF46B19B…))
   ChangeId=97F47E55…
   NodePosX=-448
   NodeGuid=B47EA575…
   CustomProperties Pin (…)
End Object
```

- The transient path is `/Engine/Transient.<ScriptName>:NiagaraScriptSource_0.NiagaraGraph_0.<NodeName>`.
- `ChangeId` is a per-node GUID. Any value parses.
- **A property equal to its default is omitted** — `NodePosY` is simply absent when the node
  sits at y=0. Writing it explicitly is still accepted.
- No Niagara node overrides `PostPasteNode` or `ReconstructNode`, so the pin set that goes in
  is the pin set that comes out. Dynamic pins survive verbatim.
- `UNiagaraNodeOutput::CanDuplicateNode()` is `false`, so an Output node is never in a copy and
  must not be in a payload. Same for `NiagaraNodeEmitter`.

## Pins

```
CustomProperties Pin (PinId=63ABDDC2…,PinName="Index",PinType.PinCategory="Type",
  PinType.PinSubCategory="",
  PinType.PinSubCategoryObject="/Script/CoreUObject.ScriptStruct'/Script/Niagara.NiagaraInt32'",
  PinType.PinSubCategoryMemberReference=(),PinType.PinValueType=(),PinType.ContainerType=None,
  PinType.bIsReference=False,PinType.bIsConst=False,PinType.bIsWeakPointer=False,
  PinType.bIsUObjectWrapper=False,PinType.bSerializeAsSinglePrecisionFloat=False,
  DefaultValue="0",AutogeneratedDefaultValue="0",
  LinkedTo=(NiagaraNodeConvert_1 59D4BD2F…,),
  PersistentGuid=00000000000000000000000000000000,bHidden=False,bNotConnectable=False,
  bDefaultValueIsReadOnly=False,bDefaultValueIsIgnored=False,bAdvancedView=False,bOrphanedPin=False,)
```

(Written on one line in the file; wrapped here.)

| Piece | Meaning |
|---|---|
| `PinType.PinCategory` | `"Type"` for a value type, `"Class"` for a data interface, `"Misc"` for the add-pin. Also `"Enum"`, `"StaticType"`, `"StaticClass"`, `"StaticEnum"`. |
| `PinType.PinSubCategory` | `"ParameterPin"` on Map Get / Map Set parameter pins, `"DynamicAddPin"` on the `+` row, `""` otherwise. |
| `PinType.PinSubCategoryObject` | The type, as `"/Script/CoreUObject.ScriptStruct'<path>'"` or `"/Script/CoreUObject.Class'<path>'"`. `None` on the add-pin. |
| `Direction="EGPD_Output"` | Present only on outputs. |
| `PinFriendlyName=INVTEXT("…")` | Carried on parameter pins; the label the graph draws. Niagara uses `INVTEXT`, the Material Editor `NSLOCTEXT`. |
| `LinkedTo=(<NodeName> <PinId>,)` | Written on **both** ends of every wire. |
| `PersistentGuid` | Zero except on Map Get parameter output pins, which are paired with their default pins through it. |
| `PinToolTip` | Carried on operator pins and on Map Get default pins. |
| `DefaultValue` / `AutogeneratedDefaultValue` | Plain text parsed by the type's editor utility. One place only — there is no second copy on a property, so Niagara has none of the material value-drift trap. |

### Operator pins carry their own defaults

An `Op` pin's default comes from the op, **not from its type**. A real `Numeric::Lerp` copy reads:

```
PinName="A"      PinFriendlyName=NSLOCTEXT("NiagaraOpInfo", "First Function Param", "A")   DefaultValue="0.0"
PinName="B"      PinFriendlyName=NSLOCTEXT("NiagaraOpInfo", "Second Function Param", "B")  DefaultValue="1.0"
PinName="C"      PinFriendlyName="Alpha"   PinToolTip="A value typically between 0 and 1…"  DefaultValue="0.0"
PinName="Result" PinToolTip="Result"       Direction="EGPD_Output"                          (no default)
```

`B` is **1.0**, so an emitter that substitutes the type default pastes a Lerp that quietly
interpolates towards zero. All five parts of `FNiagaraOpInOutInfo(Name, Type, Friendly, Tooltip,
Default)` are therefore captured by `niagara/generate-ops.mjs`.

`PinFriendlyName` is written verbatim, `NSLOCTEXT` and all. This emitter **omits it when it
would repeat the pin name** — the drawn label and the paste are identical either way, and it
keeps the payload readable. `"Alpha"`-style names, which differ, are always written.

## Node types seen in a real scratch pad

| Class | Carries |
|---|---|
| `NiagaraNodeInput` | `Input=(VarData=(…),Name="InputMap",TypeDefHandle=(RegisteredTypeIndex=95))`, `CallSortPriority` |
| `NiagaraNodeParameterMapGet` | `PinOutputToPinDefaultPersistentId` pairing each parameter output pin to its default input pin |
| `NiagaraNodeParameterMapSet` | pins only — `Source` in, `Dest` out, one input pin per parameter written |
| `NiagaraNodeCustomHlsl` | `CustomHlsl="…"` (escaped `\r\n`), `Signature=(Inputs=(…),Outputs=(…))` |
| `NiagaraNodeConvert` | `Connections(N)=(SourcePinId=…,SourcePath=("X"),DestinationPinId=…,DestinationPath=("X"))`, `ExpandedItems`, `AutowireBreakType` |

### Function calls

```
Begin Object Class=/Script/NiagaraEditor.NiagaraNodeFunctionCall Name="NiagaraNodeFunctionCall_195" ExportPath="…"
   FunctionScript="/Script/Niagara.NiagaraScript'/Niagara/Functions/Rotation/LerpQuaternion.LerpQuaternion'"
   CachedChangeId=0EA505954FBBD01D4B2DB08975C719C1
   FunctionDisplayName="LerpQuaternion"
   …
   Pin PinName="Quat A"       Quat4f          DefaultValue="0.000,0.000,0.000,1.000"
   Pin PinName="Quat B"       Quat4f          DefaultValue="0.000,0.000,0.000,1.000"
   Pin PinName="Lerp Factor"  NiagaraFloat    DefaultValue="0.000000"
   Pin PinName="Quaternion"   Quat4f  out     bDefaultValueIsIgnored=True
```

- The asset reference is `Class'<PackagePath>.<AssetName>'`, so the asset name repeats.
- **Pin names are the called script's own input names, verbatim** — spaces included, no
  namespace prefix. They are whatever the asset's author typed, typos included, so they cannot
  be derived and have to be read off the asset or a real copy.
- **An output pin carries `bDefaultValueIsIgnored=True`** and no `DefaultValue`. This is the one
  place the flag differs; Map Get, Map Set and operator outputs all leave it `False`.
- Function-call pins carry no `PinFriendlyName` or `PinToolTip`.
- `CachedChangeId` caches the called script's change id. Leaving it at the default marks the
  node stale, so Niagara rebuilds the pins from the asset — which is what you want for pins a
  spec declared by hand. This emitter omits it deliberately.
- Default text is formatted per type: a float as `"0.000000"`, a vector as `"0.000,0.000,0.000"`,
  a quaternion as identity `"0.000,0.000,0.000,1.000"`. Operator pins use the op's own strings
  instead (`"0.0"`, `"1.0"`), so the two contexts do not agree on formatting and neither has to —
  the value text is parsed by the type's editor utility, not compared.

A Map Get parameter pin comes in pairs: the **output** pin (`PinName="Module.LifeTime"`,
`Direction="EGPD_Output"`, non-zero `PersistentGuid`) and a matching **input** pin with no
`PinName`, a `PinToolTip="Default value for Module.LifeTime …"`, and its own `PersistentGuid`.
`PinOutputToPinDefaultPersistentId` maps the first to the second.

## Type indices

`FNiagaraVariable` stores its type as `FNiagaraTypeDefinitionHandle`, whose only `UPROPERTY` is
`int32 RegisteredTypeIndex` (`NiagaraTypes.h:1275`) — an index into a registry built at runtime.
Binary serialisation expands it through a custom `operator<<`; **the text path has no such hook,
so the raw index is what lands in T3D.**

That looked like the one thing that could sink hand-authored payloads. It does not:

- Two captures of the same graph, taken across a **full editor restart**, were byte-identical.
  The index is stable for a given engine build and plugin set.
- It is *not* portable across engine versions: a UE 5.1 capture on blueprintue.com shows
  `NiagaraParameterMap` at 69, where UE 5.8 has 95.
- Only nodes with an `FNiagaraVariable` property are affected — `Input`, `CustomHlsl`'s
  `Signature`, and the `OutputVars` of `If` / `Select` / `StaticSwitch`. A graph of
  Map Get → ops → Map Set does not touch it.

Observed on UE 5.8:

| Index | Type |
|---|---|
| 73 | `NiagaraDataInterfaceArrayFloat4` |
| 74 | `NiagaraDataInterfaceArrayColor` |
| 95 | `NiagaraParameterMap` |
| 99 | `NiagaraFloat` |
| 101 | `NiagaraInt32` |
| 103 | `Vector2f` |
| 106 | `LinearColor` |
| 107 | `NiagaraPosition` |

Regenerate the table from a fresh capture when moving engine version.

## Reading a capture

`node reference/survey.mjs <file.t3d>` prints the pin encoding of a Material Editor copy. For a
Niagara copy the payload has to be un-Base64'd first; `niagara/decode.mjs` does that and writes
the inner node T3D beside it.
